## Methodology

The content rules for every test case — full navigation path, preconditions in test data, verifiable expected results, the undefined-behavior policy, hypothetical failure tests, the required cases per data-rule type, the general edge-case checklist and the final review — are in the `qa-test-case-writing` skill. Follow it for every row; the steps below say what to produce, not how to word it.

0. **Read the app knowledge file** (`<qa-repo>/app-knowledge.md`) first, creating it from `templates/app-knowledge-template.md` if it's missing, and keep it updated as you read the sources (see `qa-test-case-writing` §1).
1. **Require at least one real grounding source before doing anything else.** Figma and a spec/LLD doc are both asked for up front; either may be explicitly marked not applicable with a stated reason (e.g. "no UI, no Figma"), but if neither a Figma link nor a spec/LLD doc nor any other QA-supplied doc exists, stop and ask the human — there is nothing to ground test cases in otherwise. Never invent screens or flows from just a feature name.
2. **Enumerate frames and states via the `figma` MCP server** when a Figma link exists. Use `get_metadata` to see the file/page/frame structure, `get_design_context` to pull component and content detail, and `get_screenshot` for anything ambiguous. Include loading/empty/error/success/permission/validation variants as distinct states, not just the "happy path" frame. Review every frame in the relevant section (not only the linked ones) and build the static-text table (`qa-test-case-writing` §2) before writing test cases.
3. **Read the spec/LLD** when one exists, for functional requirements and business logic Figma doesn't show (validation rules, edge-case behavior, backend constraints). Ground visual/interaction detail in Figma and functional/business-logic detail in the spec. If the two sources describe the same thing differently, don't silently pick one — log it under Open Questions.
4. **Derive functional test cases per screen/flow**, one sub-section per screen in navigation order, naming the actual button/label text and layout from the design where one exists, or the behavior described in the spec where it doesn't.
5. **Derive the remaining sections** in the order of `qa-test-case-writing` §7: Error Screens (every error screen in the sources, Figma-only ones included), Edge Cases From Design/Spec (including the required cases per data-rule type), API Failures (hypothetical — one row per screen or action), and Universal edge cases (the general checklist), then fill the Edge-Case Checklist Report item by item.
6. **Write accessibility checks only when needed** — when the sources call for accessibility or the human confirmed which tests to include (the command asks upfront); otherwise leave the section out. When written, they are the last section, as scenario-level test steps in plain language — no standard IDs, no reference to `ono-mobile-dev-plugin`'s `standards/` docs. There is no separate i18n/RTL section; a device language other than the app language is a universal edge case (`qa-test-case-writing` §6.1, §7.2).
7. **Log anything the sources leave ambiguous** (an undesigned error state, an unclear interaction, a Figma/spec conflict) as an open question for a designer/PM/dev to resolve — never silently guess. The affected test case is still written, per the undefined-behavior policy: the certain part in its expected result, only `לא מוגדר באיפיון: …` in its comments — never a guess.
8. **Record every source actually consulted** — Figma link, spec/LLD path/link, and anything else QA supplied — into the "Input Sources" table, including explicit `N/A — <reason>` rows for any category that doesn't apply. This is what `/sync-qa-test-plan` later re-checks when sources change.
9. **Populate `templates/qa-test-plan-template.md` in full**, including "Screens & Flows Covered" with enough detail (frame names/links or spec section references) that `/check-qa-coverage` can later match it against the dev handoff's "Screens & Flows Touched".
10. **Export the same test cases to a Hebrew/RTL Excel file** per `templates/qa-test-cases-xlsx-schema.md`: take every test case just authored (Functional, Error Screens, Edge Cases From Design/Spec, API Failures, Universal, and Accessibility when present), write each in natural, idiomatic Hebrew (not a literal machine translation) using the fixed vocabulary of `qa-test-case-writing`, as the schema's Summary/Action/Expected Result/Test Data/Comments columns, write them to a temporary JSON file in the schema's shape, and run `node "${CLAUDE_PLUGIN_ROOT}/scripts/build-test-cases-xlsx.mjs" <input.json> <output.xlsx>` to produce `test-cases.xlsx`. Do the visual check the schema describes when LibreOffice is available.
11. **Run the final review** (`qa-test-case-writing` §8) on both files before presenting them, and report: total test cases, the coverage map with anything not covered and why, every Figma–spec difference, and what is still open.

## Unchanged constraints

- Never read the code repo, dev's implementation plan, or dev's QA handoff doc — that coupling belongs entirely to Phase 2 (`/check-qa-coverage`). Phase 1 stays independent of dev's progress, whether grounded in Figma, a spec/LLD, or both.
